1Manager · before service

Set the rules

The manager decides what can be offered and how generous the system is allowed to be. Nothing here targets a table yet. It sets the menu of possible deals and the limits every deal must pass.

What it uses

  • Flash offers page5 deals: price, daily limit, priority, on/off
  • Menu & inventoryitem cost and stock, used for profit and availability
  • Venue settingsprofit floor S$2.50, score 65, 78% chance, 15% control
  • lib/seed.tsstarting deals and menu

OutcomeA rulebook the engine reads on every order.

2Server · guest sits down

Open the table and check ID

Staff opens a visit on T04. Opening a visit secretly puts it in the comparison (control) group 15% of the time. Ticking the 18+ box is what later allows alcohol rewards.

What it uses

  • action: "session"creates the visit, rolls the 15% control group
  • action: "flags"age verified, intoxicated, blocked
  • table_sessionsone open visit per table, enforced by the database

OutcomeT04 is open, ID-checked, and not in the control group.

3Guest · optional

Recognise the guest

A guest can sign in on their own phone by SMS, then scan the table QR and give the server a 6-digit check-in code. Alternatively, the POS sends a loyalty card reference. In live mode a deal is only possible once the guest is identified. That is how the 30-day limit is enforced per person.

What it uses

  • /member pageSMS sign-in, membership number TP-XXXXXXXXXX
  • member-core.tscheck-in code, single use, this table only
  • customerRefloyalty reference from the POS, hashed

OutcomeThe visit is linked to a verified customer. Our run used a POS loyalty reference.

4POS · order sent

The order arrives

The till sends the order (2 × Tiger draught, S$24.00) to TablePulse. Repeated messages are ignored, stock is checked and taken off, and the order is saved. The simulator page sends the same message a real POS would.

What it uses

  • POST /api/pos/eventssigned message from the till
  • ingestOrder()dedupe by event ID, stock check, save
  • POS simulator pagedemo stand-in for the till

OutcomeOrder saved. This triggers a decision. Waiting never does.

5Engine · in milliseconds

Decide whether this table gets a deal

The engine runs the order through a series of gates. Each deal either survives or is dropped with a written reason. The survivor with the highest score is offered, subject to a final 78% chance.

What it uses

  • lib/engine.ts → evaluate()the whole decision
  • safetyReasons()can this table get anything at all?
  • matches()which deal fits this basket?
  • scoreprofit + stock + priority + preference + random
  1. Real paid order, no other discount2 × Tiger, full price
  2. Not blocked, not paused, first chance this visitnew visit on T04
  3. Verified customer (live mode)POS loyalty reference
  4. Not in control group (15%)1 in 7 visits get nothing so results can be compared
  5. Basket matches a deal2+ beers and no snack → “A little crunch”. The other 4 deals didn’t fit
  6. Item in stock, ID OK for alcoholcorn chips aren’t alcohol
  7. Daily limit, 60-day repeat rulewithin today’s limit of 25
  8. Profit above S$2.50S$3.90 − S$1.20 cost = S$2.70
  9. Score above 6565.4, only just
  10. 78% chanceshown

OutcomeShown: “A little crunch”, corn chips for S$3.90, score 65.4, code 7EK8U9.

6Guest · table tablet

The table screen shows the deal

The tablet at T04 checks in every 3 seconds using a signed link that only works for this visit. It shows the deal, the price, a 12-minute countdown and the code. It never shows the guest’s name or history.

What it uses

  • /display/[token]signed, expires when the bill closes
  • public-screen.tsxwhat the guest sees
  • duration: 12minutes the deal stays open

OutcomeThe guest sees an offer that makes sense for their order.

7Server · guest says yes

Staff redeems the code

The guest tells the server the code. The server opens T04 and enters it. Every check runs again, and the code only works on this table’s current bill. The reward is added as a separate line, stock drops by one, and revenue and profit are recorded.

What it uses

  • redeem()re-checks safety, expiry, stock, profit
  • offer_redemptionsone redemption per code, enforced by the database
  • 5-try lockoutblocks code guessing for 5 minutes

OutcomeBill goes from S$24.00 to S$27.90. The deal is redeemed.

8Guest · rest of the visit

One reward per visit

The screen goes back to the menu and the QR. This visit can’t get another deal, even if they order more, and the guest can’t get another subsidised deal for 30 days.

What it uses

  • offerReceivedvisit has had its one reward
  • historyper-customer 30-day and 60-day limits

OutcomeNo repeat deals, so guests can’t game it.

9Manager · during and after service

See what it earned

Every redemption feeds the dashboard and analytics. Profit here is reward sales minus item cost. It assumes the guest would not have bought the item anyway, so treat it as an estimate rather than proven extra profit.

What it uses

  • Overviewlive tables, active deals, revenue, profit
  • Analyticsresults by deal type, control comparison, CSV export
  • Activity logevery decision and staff action

OutcomeCorn chips: S$3.90 revenue, S$2.70 profit, S$4.10 discount given.

Captured in demo mode, where a verified customer isn’t required. In live mode, step 3 is required before any deal can appear. The run included the three fixes from the simulation. The screens look the same without them.
